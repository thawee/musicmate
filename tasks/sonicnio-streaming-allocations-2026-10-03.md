# Streaming allocation audit (2026-10-03)

Source audit of the current working tree. No production changes or new allocation/throughput measurements. The priorities below reflect allocation frequency, byte volume and ownership risk; actual ART allocation and GC effects still require profiling.

Follow-up: the lazy FrameDecoder proposal is now implemented and measured independently in [the full report](performance/sonicnio-lazy-flac-2026-10-03/REPORT.md). Host metadata allocation falls 99.2%; 222 core/UPnP tests pass. [Phone follow-up](performance/sonicnio-lazy-flac-2026-10-03/PHONE_RESULTS.md) confirms isolated ART allocation falls 99.1%, but recommends holding the change from release due to adverse app PSS and per-run seek maxima. The remaining proposals are still research.

## Findings

| Priority | Site and frequency | Candidate reduction | Constraints |
| --- | --- | --- | --- |
| 1: converted FLAC startup/seek | `FlacToWav.open()` consumes all metadata to obtain STREAMINFO. Reading the last metadata block creates a FrameDecoder with two long[65536] arrays: 1,048,576 bytes of element storage, even for metadata-only/HEAD requests. Actual body streaming opens a second decoder and repeats this allocation. | Construct the frame decoder lazily at first audio decode/seek, preserving metadata-only behavior. | Preserve stream validation, end-of-metadata checks, close and seek behavior. This avoids a concrete unnecessary MiB per completed metadata scan without introducing a pool. |
| 2: FLAC metadata | `FlacDecoder.readAndHandleMetadataBlock()` allocates byte[length] and Object[2] for every metadata block. Both metadata probe and body startup read blocks, including ignored pictures/padding. | Add an internal streaming metadata path that reads required STREAMINFO/SEEKTABLE and skips irrelevant payloads without materializing them. | Keep the existing public API that returns block bytes; preserve required metadata validation and bounds/truncation behavior. Large embedded artwork makes the potential savings much larger than small callback objects. |
| 3: generated PCM, continuous | `StreamingResponse.start()` allocates a heap ByteBuffer and backing byte[] for every acquired chunk, up to 64 KiB. Current batching already combines small producer writes, but draining releases reservations and discards buffers. | If profiling shows significant churn, use a capped chunk recycler shared through the existing budget, or producer-leased writable chunks in a separate experiment. | Pool resident bytes must include idle buffers as well as producer/queue/pending ownership. Return a chunk only after final socket drain or cancellation; never reuse a decoder's array while queued. Variable/small startup chunks complicate size classes. Keep prompt startup and 16-slot queue/backpressure. |
| 4: converted FLAC seek | FlacToWav owns int[channels][65536]; `seekAndReadAudioBlock()` separately allocates another array of that size for seek decoding then copies the chosen suffix. Stereo element storage is 524,288 bytes for each array. | An internal seek API can accept/reuse the caller's scratch workspace, with explicit output/offset semantics, or use decoder-owned reusable workspace. | Test nonzero offsets, mid-frame seeks, end-of-file, no seek table, multi-channel input and byte-identical ranges. Avoid global mutable decoder sharing. Existing scratch is reused across frames within one seek, so this is per seek, not per frame. |
| 5: write attempts and wakeups | `handleWrite()` supplies a capturing lambda to `streaming.park(...)` on each unfinished write attempt. Each PCM buffer acquisition supplies `() -> closed`; each requestWrite call creates PendingWrite plus a ConcurrentLinkedQueue node. | Bind cancellation supplier and response-specific wake callback once per response. If wakeup counts justify it, coalesce pending-write notifications while preserving response identity. | A callback cannot merely capture a key and consult its latest response: stale wakeups must never activate a successor response. Keep park/recheck ordering and cancellation races correct. Capturing lambdas are source candidates; ART may eliminate some allocations. |
| 6: converted FLAC frames | FrameInfo.readFrame creates a new FrameInfo per parsed frame. | Consider a decoder-private mutable frame result only if allocation profiling shows it matters. | Preserve public APIs that return distinct metadata objects. These objects are far smaller than PCM/metadata arrays. |
| 7: each HTTP response/seek | buildHeaders uses StringBuilder → String → UTF-8 byte[] → ByteBuffer, plus a header map and entries. FileResponse also constructs metadata strings, MessageDigest and digest/ETag output. | If seek profiling identifies header work, evaluate direct bounded header encoding, static protocol tokens and response-local/scoped digest reuse. | Header content, UTF-8 behavior, validators and concurrent writes must remain identical. Do not cache stale file attributes or share mutable MessageDigest unsafely. Earlier ETag/date work already removed most measured encoding allocation; further savings are unmeasured. |
| Low | WAV header creates a 44-byte buffer and three small literal byte arrays. Producer setup creates a long[1] counter, callbacks and Future once per response. Diagnostics record one terminal ResponseEvent and bounded history snapshots when requested. | Static WAV marker constants or primitive state in a response-local sink are possible. | Small savings. Do not remove useful diagnostics or complicate concurrency for these before larger sites are profiled. |

## Source anchors

- [AudioBufferBudget](../core/src/main/java/apincer/music/core/http/AudioBufferBudget.java): counts active generated buffers, not idle pooled memory; a pool requires extending that accounting.
- [NioHttpServer](../core/src/main/java/apincer/music/core/http/NioHttpServer.java): `requestWrite`, `handleWrite`, `HttpResponse.buildHeaders` and `processResponseQueue`.
- [FlacToWav](../core/src/main/java/apincer/music/core/codec/FlacToWav.java): metadata probe, reusable 64 KiB output and per-channel samples, WAV header.
- [FlacDecoder](../library/JustFLAC/src/java/io/nayuki/flac/decode/FlacDecoder.java): metadata materialization, eager frame decoder and extra seek sample storage.
- [FrameDecoder](../library/JustFLAC/src/java/io/nayuki/flac/decode/FrameDecoder.java): two 65,536-element long workspaces per decoder.

- [AlacToWav](../core/src/main/java/apincer/music/core/codec/AlacToWav.java): FFmpeg pipe reader with one reusable 64 KiB array per response. Native FFmpeg allocations are outside this Java audit.

## Already reused; preserve these paths

The native-file write loop has no explicit application object allocation per transfer iteration; it uses primitive counters and FileChannel.transferTo. Platform internals may allocate and need separate profiling. Header buffers are built once per response and retained across partial writes.

FlacToWav reuses its 64 KiB output array and sample arrays across decoded frames; AlacToWav reuses its pipe read array. StreamingResponse must currently copy from these reusable arrays into independently owned queued buffers. Queue slots themselves are in an ArrayBlockingQueue backing array, so there is no linked queue node per PCM chunk. Long-lived budget, admission and queue objects are not created per packet. Do not count allocations in the separate whole-buffer AudioDecoder analysis utility as live SonicNIO streaming: the audited route calls FlacToWav/AlacToWav.

Small-write PCM batching and ETag/date encoding have already been implemented and benchmarked in [PERFORMANCE](../PERFORMANCE.md). Parser copy savings are also measured, but the combined parser/copy change remains held from release due to repeated higher phone seek maxima. Reduced allocation alone does not establish a latency or throughput improvement.

## Proposed order and proof

1. Profile converted FLAC metadata/HEAD and repeated range seeks first, including tracks with large artwork/padding. Attribute allocations to stacks and distinguish Java from FFmpeg/native memory. Record allocation bytes/rate, GC events, response preparation, first byte, seek p95/p99/max and memory high-water marks on the phone.
2. Test lazy frame-decoder creation independently; it has a concrete avoidable allocation and less ownership risk than pooling. Then test metadata skipping and seek workspace reuse as separate candidates with FLAC correctness/range fixtures.
3. Bind recurring callbacks once, testing stale response wakeups, stalled producers and disconnect races. Pool PCM only if sustained converted-stream allocation/GC remains significant; maintain a bounded total retained footprint.
4. Compare isolated APK changes using interleaved runs and preserved hashes/raw results. Verify original/converted range byte hashes, partial writes, cancellation, resource release and core/UPnP suites. Reject repeated seek-tail regressions even if microbenchmark allocation improves. Do not claim Netty superiority without matched workloads.

These are research candidates, not an approved implementation/release result. Quantities above are array element storage calculated from source; object headers, alignment, metadata sizes and runtime optimization are excluded.
